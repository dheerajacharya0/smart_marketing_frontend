# Partner-tier gate, not the flag, blocks coexistence

The generic "already registered… disconnect it" rejection that +916353572410 is still hitting — even with `featureType: "whatsapp_business_app_onboarding"`, `sessionInfoVersion: "3"`, and the correct user choice all confirmed live in production — is best explained by a **server-side eligibility gate that is independent of anything the client sends**: Meta's own documentation for the coexistence flow lists "You must already be a Solution Partner or Tech Provider" as a standalone Requirement, separate from and *not* satisfied by the Advanced Access on `whatsapp_business_management`/`whatsapp_business_messaging` this app already holds ([Meta: Onboarding Business App Users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users)). The strongest piece of corroborating evidence is structural, not circumstantial: Meta's error reference splits into two non-overlapping tables — a generic, uncoded "phone setup errors" table (where the exact "up to 3 minutes" text the device is showing lives) and a dedicated, numerically coded coexistence table in the `3441xxx`/`2655xxx` range ([Embedded Signup Flow Errors](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/errors.md)). Hitting the uncoded generic table is itself evidence that Meta's backend never entered the coexistence code path at all, despite the correct flag arriving — which is exactly the symptom a missing partner-tier gate would produce, since Meta documents no error code for "flag sent but partner status missing," only a plausible silent fallback to the standard new-number flow. Two other candidate gates — an outdated WhatsApp Business app version and an undocumented "stale registration" cooldown — were checked and are weaker fits: an old app version has its own distinct, differently-worded error code (4563015), and no Meta source documents any cooldown keyed to registration history, only vendor folklore. The single most important next action, ahead of any Meta Business Manager changes, is to instrument the Embedded Signup `ERROR` postMessage listener to capture the actual `error_code` and `session_id` Meta is returning — because that one data point will immediately confirm or rule out the Tech Provider theory, and Meta explicitly asks for both values before it will investigate further.

## The rejection text itself shows coexistence mode never turned on

The most load-bearing finding across this research is structural rather than anecdotal: Meta's official "Embedded Signup Flow Errors" page documents coexistence-specific failures as a distinctly numbered table — `3441041` (number not tied to the selected business), `3441045` ("isn't eligible to connect… eligibility can't yet be determined"), `3441042` (region unavailable), `2655093` (business already shares the account with a partner), `2655082` (linked to a Facebook Page), `3441049`/`2655094` (already registered with another product, 15-minute wait), `3441047` (incompatible with Marketing Messages), and `4563015` (app version too old) — all living in the "WhatsApp Business app user onboarding" section of that page ([Embedded Signup Flow Errors](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/errors.md)). The text the test device is actually showing — "This number is registered to an existing WhatsApp account. To use this number, disconnect it… up to 3 minutes" — carries **no numeric code at all** and sits in a separate, generic "Phone setup errors" table on that same page, the one used for ordinary new-number registration conflicts. No source found in this research documents any mechanism by which a genuine coexistence-path rejection would surface through the uncoded generic table instead of its own coded table; the two tables appear to correspond to two different backend code paths, not two renderings of the same one. That makes the observed error itself the strongest available signal that the backend processed this attempt as an ordinary new-number signup, not as a coexistence attempt that was then correctly declined — which reframes the debugging question away from "why did coexistence reject this number" and toward "why didn't this request enter the coexistence path despite sending the documented flag."

## Tech Provider/Solution Partner status is a separate, likely-unmet gate

Meta's documentation draws an explicit, unambiguous line between two independent prerequisites for this flow. The coexistence onboarding page's Requirements section lists five items verbatim: WhatsApp Business app version 2.24.17+, **"You must already be a Solution Partner or Tech Provider,"** knowledge of Cloud API, a working webhook callback, and Embedded Signup with session logging — and notably does not mention Advanced Access or either WhatsApp permission anywhere in that list ([Meta: Onboarding Business App Users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users)). Separately, Meta's Solution Providers overview page describes Advanced Access via App Review as its own, independent gate, with its own distinct failure modes — API calls failing with error 200 without Advanced Access on `whatsapp_business_management`, or the messaging permission simply not appearing in Embedded Signup without Advanced Access on `whatsapp_business_messaging` ([Meta: Solution Providers Overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/overview/)). Nothing on either page ties the two together, and nothing suggests holding Advanced Access (which this app secured on 2026-10-23, per the project's own history) implies or substitutes for Solution Partner/Tech Provider enrollment. Meta also does not document the exact mechanical consequence of sending `featureType=whatsapp_business_app_onboarding` without that partner-tier status — there is no confirmed error code for it — but the most consistent inference, given that the observed failure lands in the generic uncoded table rather than the coexistence-specific one, is a silent server-side fallback: the backend declines to open the "connect my existing WhatsApp Business app number" branch at all and instead evaluates the request as an ordinary new-number signup, which then correctly refuses a number that's live on the Business app. Status here is not visible through any Graph API field or Business Suite badge found in this research; it is tracked only as an application outcome, reachable through the App Dashboard's WhatsApp Quickstart ("Scale your business" card) and Partner Hub, with approval requiring Business Verification and acceptance of Tech Provider Terms, generally reported by vendors (not Meta) to take two to five business days for the verification step alone ([Meta: Solution Providers Overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/overview/); vendor estimate: [Infobip Tech Provider setup](https://www.infobip.com/docs/whatsapp/tech-provider-program/setup-and-integration.md)).

## Weaker candidates: app version and registration-history cooldowns

Two other eligibility gates were run down and both are poorer fits for the specific symptom observed. Meta's own documentation still lists **WhatsApp Business app version 2.24.17 or higher** as the floor, unchanged since at least mid-2025 and corroborated by every vendor source checked ([Meta: Onboarding Business App Users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users); [Infobip](https://www.infobip.com/docs/whatsapp/manage-integration/coexistence)) — but an outdated app has its own documented, differently-worded error, **code 4563015** ("Update your WhatsApp Business App to the latest version"), which sits in the same coexistence-specific table discussed above and is textually nothing like the generic message the device shows ([Embedded Signup Flow Errors](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/errors.md)). It should still be confirmed on the physical test device (Settings > Help > App Info — no Graph API field exposes the installed app version remotely), but it is not the leading explanation. A registration-history or "stale number" cooldown is an even weaker fit: Meta's own docs expose exactly one same-app repetition limit, a 72-hour/10-request register-or-deregister rate window that triggers error `133016` and applies regardless of which app registered the number before ([Meta: Register a Business Phone Number](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/registration/)); no Meta source documents any cooldown keyed to *registration history itself*. The numbers vendors cite — "7+ days of active use," "1–2 month cooldown after deleting a prior WABA" — are explicitly self-described by at least one of those vendors as inferred "from available information and insights from web sources," not sourced to Meta, and conflict with each other by an order of magnitude ([ChakraHQ](https://chakrahq.com/article/issues-whatsapp-coexistence-onboarding-setup/)). Meta's own "Reconnect Offboarded Coexistence Clients" doc in fact describes the opposite: a same-partner, same-app reconnection path designed to restore a known WABA within minutes, with no multi-day penalty, as long as no other partner has intervened during an undefined "reconnection window" ([Meta: Reconnect Offboarded Coexistence Clients](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/reconnect-offboarded-coexistence-clients/)). Since +916353572410 is reported live and actively used — not abandoned, not recently deleted from another provider — this gate is the least likely of the three candidates, though it is worth explicitly ruling out whether the number has *any* prior Cloud API/WABA history with a different provider, since that would instead trigger the distinct, Meta-confirmed "shared credit line with a partner" error (`#2655093`) rather than the error observed here ([Meta Developer Community thread #1635723110883422](https://developers.facebook.com/community/threads/1635723110883422/)).

## Capturing the real error code is the one action that resolves the ambiguity

Every theory above is currently a hypothesis because the generic UI text is, by Meta's own design, not diagnostic — it is deliberately coarse. Meta's "Embed the Signup Flow" documentation defines a structured `postMessage` event contract: all events carry `type: 'WA_EMBEDDED_SIGNUP'` and should only be trusted after verifying the message origin is a facebook.com domain; the `ERROR` event specifically carries `data.error_message`, `data.error_code`, `data.session_id`, and `data.timestamp`, with Meta's docs explicitly annotating `error_code` and `session_id` as "include this when contacting support" ([Meta: Embed the Signup Flow](https://developers.secure.facebook.com/docs/whatsapp/embedded-signup/embed-the-flow)). Concretely, the fix is to add a `window.addEventListener('message', ...)` handler (verifying `event.origin` against Facebook's domain and `event.data.type === 'WA_EMBEDDED_SIGNUP'`) around wherever `lib/facebook-sdk.ts` currently invokes `FB.login()`, log `event.data.data.error_code`, `error_message`, and `session_id` on an `ERROR` event, and reproduce the rejection once with that listener live. The result is immediately diagnostic: a numeric code in the `3441xxx`/`2655xxx` range (e.g., `3441045`, `2655093`, `3441049`) would mean the backend *did* enter the coexistence path and is rejecting the number for a specific, documented coexistence reason — pointing back toward app version, Page linkage, partner credit-line sharing, or region, not toward Tech Provider status. No code at all, or a code that maps only to the generic table, would confirm the coexistence path never activated — strongly reinforcing the Tech Provider/Solution Partner theory as the root cause. Either outcome also produces exactly what Meta's support channel requires to act: the escalation path for a non-partner app is the standard developer support form (developers.facebook.com/support) and the Meta Developer Community forum, not Direct Support, which Meta documents as gated to "enterprise developers, including partners and managed partners" — i.e., likely inaccessible until Tech Provider/Solution Partner status is obtained ([Meta: Support](https://developers.facebook.com/documentation/business-messaging/whatsapp/support.md)). A ticket or community post should include the app ID (653350917280402), the WABA ID, the phone number, the exact `error_code` and `session_id` from the captured event, a precise timestamp with time zone, and should proactively note that Advanced Access on `whatsapp_business_management` and `whatsapp_business_messaging` was already granted 2026-10-23 — preempting the first-line troubleshooting suggestion the support docs otherwise lead with.

## Conclusion

The research converges on a single actionable hierarchy: first, instrument and capture the real `error_code`/`session_id` — this costs almost nothing and removes all ambiguity about which of the two Meta error tables the rejection is actually coming from. Second, and in parallel, check this app's Solution Partner/Tech Provider enrollment status in the App Dashboard's Partner Hub / WhatsApp Quickstart, since Meta's own documentation treats that status as a standalone, unmet-by-default requirement that the already-approved Advanced Access does not satisfy — and the symptom profile (a correctly-sent flag producing a generically-coded, non-coexistence error) matches a missing partner gate better than any alternative explanation surfaced in this or the prior research pass. If Tech Provider/Solution Partner enrollment turns out to be the answer, it changes the shape of the fix entirely: this is not a client bug fixable by another code change, but a business-process step (Business Verification plus Tech Provider Terms, vendor-estimated at two to five business days) that has to happen in Meta's partner program before any amount of correct `featureType` plumbing can take effect.
