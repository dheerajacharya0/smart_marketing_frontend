# Stale WABA number cleanup cannot be automated away

The manual password-gated deletion your team just performed in Meta Business Suite is not a workaround for a missing feature — it is the **only** operation Meta exposes for this problem, and it has no API form at all. Meta's Graph API gives backends exactly one number-lifecycle call, `deregister`, which explicitly does not delete a number or clear a stale WABA attachment, and is additionally blocked outright on any coexistence-linked number ([Register/Deregister a Phone Number](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/registration)). The `phone_numbers` edge on a WhatsApp Business Account — the only other place a number-removal call could live — documents POST only; GET, UPDATE, and DELETE are all explicitly marked "You can't perform this operation on this endpoint" ([phone_numbers edge reference](https://developers.facebook.com/docs/graph-api/reference/whats-app-business-account/phone_numbers/)). Even if that gap didn't exist, your backend has no standing to touch the old WABA in the first place: Meta's access model is asset-based, not identity-based, so the fact that the same customer personally administers both Business Managers is legally and technically irrelevant to what your app's token is allowed to do. The realistic product fix is not "automate the deletion" but "stop treating this as a generic error, diagnose it precisely, and hand the customer one targeted, well-explained click instead of a cryptic rejection" — automation effort belongs in detection and guidance, not in trying to defeat a control Meta built on purpose.

## Three different "disconnect" operations exist, and only one has zero API surface — and it's the one you need

Meta's documentation, read carefully, splits number cleanup into three operations that are easy to conflate but behave completely differently. The first is **deregister** (`POST /{phone-number-id}/deregister`), a reversible Cloud-API-capability toggle that explicitly "does not delete a number or its message history" and cannot act on a number "in use with both Cloud API and the WhatsApp Business app" — i.e., it is powerless against exactly the coexistence-adjacent numbers that cause this class of bug ([Register/Deregister reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/registration)), a limitation independently confirmed by a BSP stating flatly that "the WhatsApp deregistration API cannot deregister a coexistence number" ([Telnyx coexistence docs](https://developers.telnyx.com/docs/messaging/whatsapp/coexistence)). The second is the **in-app "Disconnect" under Settings → Account → Business Platform** inside the WhatsApp Business consumer app on the phone — the fix Meta's own Embedded Signup error reference gives for codes `3441049` and `2655094` ("number already registered with another product," 15-minute wait), as previously documented in this project's own `diagnostic_tools.md`. This is a phone-in-hand human action with, by Meta's own admission above, no server-side equivalent at all. The third — the one that actually resolved your case — is **"Delete a business phone number"** inside WhatsApp Manager, a WABA-level asset removal that Meta's own docs reference only as a named destination anchor, never as a described mechanism, and for which the `phone_numbers` edge confirms there is no DELETE method anywhere in the Graph API. No vendor or Meta source describes a password-less, API-level path to this operation; the password re-entry is documented consistently, and only, as a Business Suite **web UI** step by independent vendor guides (Kommo, corroborated by Superchat and Wanotifier) — never as an API authentication requirement, because there is no API call for it to attach to. This matters for how you frame the problem internally: the question isn't "how do we satisfy Meta's re-auth requirement from our backend" (a hard-but-solvable integration problem) — it's "this specific destructive operation simply isn't exposed to any backend, including Meta's own partners' backends," which is a different, unsolvable-by-engineering category.

## Even with API access, your backend has no standing over the old WABA — the same person being admin of both doesn't transfer authority

A natural instinct is to ask whether your app could get the access it's missing and then call *something* programmatically. It can't, and the reason is structural rather than a documentation gap: Meta's permission model checks "does this token's business hold an asset-level Partial/Full access grant on this specific WABA," never "is the human behind this session personally an admin of the WABA's business." Missing that grant fails every relevant call with the generic Graph API error `200` ([Manage System Users](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/manage-system-users/)), and the WhatsApp permissions page confirms Advanced Access on `whatsapp_business_management`/`whatsapp_business_messaging` — which your app already has — only gates whether your app is *eligible to be granted* access to non-owned WABAs, not a substitute for the grant itself ([WhatsApp permissions](https://developers.facebook.com/documentation/business-messaging/whatsapp/permissions)). The only documented way to create that grant for a pre-existing, independently-created WABA is a human admin of the *old* business manually assigning your app's Business ID as a Partner inside Business Settings → [WhatsApp] Accounts → Partners → Assign Partner ([Asset Sharing, 360dialog](https://docs.360dialog.com/docs/resources/asset-sharing)) — the historical programmatic alternative, "Business On Behalf Of" (OBO), is deprecated and in any case only ever covered partner-*created* WABAs, not reaching into a pre-existing unrelated one ([Partner-initiated WABA creation](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/partner-initiated-waba-creation)). This asymmetry generalizes across Meta's entire asset model, not just WhatsApp: ad-account and Page agency requests are a plain API `POST` on the requester's side, but acceptance is, in every sourced mechanism, a manual action by an admin of the *target* business in a Meta-hosted UI — a "Requests inbox," "Manage Admin Roles" tab, or Business Manager review page — with `requires_admin_approval` flagged explicitly as "a review from another business admin" ([Business to Business API docs](https://developers.facebook.com/docs/marketing-api/businessmanager/business-to-business)). No sourced mechanism lets an OAuth consent screen, Embedded Signup's `extras`/`setup` parameters, or any blanket pre-authorization skip that specific click — cross-business grants are per-asset, per-request, every time.

## Meta is actively closing the one API migration path that used to exist, not opening one

It's worth checking whether a true migration call — moving the number's WABA attachment directly, rather than deleting-then-re-registering — might sidestep this entirely. It doesn't, and the trend line is the wrong direction. The legacy `migrate_phone_number=true` POST against a destination WABA is explicitly disclaimed on all three Meta migration pages checked: "Phone number migration isn't supported for accounts on the new WhatsApp account model," with the same text repeated verbatim on the primary guide, its secure-domain mirror, and the Embedded-Signup-specific variant ([Migrating Phone Numbers Among Solution Partners Programmatically](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/support/migrating-phone-numbers-among-solution-partners-programmatically)). Meta's official error-code reference corroborates this for error `2388103` ("This phone number belongs to a different Business Manager account"), whose documented solution reads simply "Not applicable" ([WhatsApp Business Management API error codes](https://developers.facebook.com/docs/whatsapp/business-management-api/error-codes)). What remains for current accounts is strictly weaker than migration: **sharing**, which "gives you access without moving" the number — it does not clear the old WABA's attachment or stop it blocking Embedded Signup — and **link/unlink in Meta Business Suite**, a UI-only action explicitly scoped to numbers "within the same business portfolio," which does not apply at all across the two unrelated Business Managers in your scenario. This closure is almost certainly tied to Meta's ongoing "WhatsApp Account Model Evolution" (WAME), a phased 2026–2028 rollout splitting the WABA concept into a phone-number-holding "WhatsApp Account" (WAAC) and a per-partner "Messaging Account" ([WAME Onboarding](https://developers.facebook.com/documentation/business-messaging/whatsapp/account-model-evolution/onboarding/)); the three migration pages' identical "new account model" language strongly suggests this is a deliberate, platform-wide design choice to prevent any party from pulling a number away from its current holder without that holder's affirmative action — not an oversight likely to be patched. Nothing in Meta's WAME documentation promises a future WAAC-to-WAAC migration endpoint, so this is not a "wait for Meta to ship it" situation either; the restriction should be treated as durable.

## The minimum unavoidable step, and the design that fits it

Collapsing all of the above: the unavoidable minimum is **one click, by an admin of the business that currently holds the stale WABA, performed on a Meta-hosted surface** — there is no way to relocate that click into your dashboard, your backend, or Meta's API, because the operation it performs (WABA-level number deletion) doesn't exist outside that surface, and the authority to even attempt it belongs to the old business's admin, not to any token your app can hold. In the scenario that actually occurred — the stale WABA sits in a Business Manager the *same* customer personally administers — this click is at least reachable without inventing a third-party-support process: they are the admin. In that case, the only remaining click is Meta's, and the product work is entirely about how you get the customer to that click correctly, which earlier research in this project already identified as largely unbuilt: Embedded Signup's v4 screens describe no in-popup "release this number" action for a number tied to an unrelated WABA, and the documented fix paths (deregister, in-app disconnect, Business Suite delete) are different operations for different states that a generic retry message cannot distinguish. The realistic design, given these constraints, has four parts, none of which claim full automation:

- **Precise, state-aware error mapping.** Capture the actual Embedded Signup `error_code`/`session_id` from the `ERROR` postMessage event (Meta explicitly asks for both before it will investigate — [Embed the Signup Flow](https://developers.secure.facebook.com/docs/whatsapp/embedded-signup/embed-the-flow)) and branch the in-dashboard message by which of the three operations actually applies, instead of a single generic "something went wrong, try again" screen. A number stuck as an *unverified, dangling WABA entry* (your diagnosed case) needs the Business Suite delete instruction; a live coexistence number needs the in-app phone disconnect instead — conflating them sends customers to the wrong fix.
- **A specific, pre-written remediation screen, not a bounce to "go to Meta."** Since the customer must leave your dashboard regardless, the product should own the explanation: name the exact WABA/Business Manager Meta reports as the conflict (to the extent the error payload or any available lookup exposes it), state in plain language that it's an old, forgotten WhatsApp setup rather than implying something is broken, and give literal step-by-step Business Suite navigation (WhatsApp Manager → Phone Numbers → delete → confirm with your Meta account password) inside your own UI, with a link to business.facebook.com rather than an unexplained redirect. (Whether a URL can deep-link directly into that specific Phone Numbers screen was not confirmed in this research and should be verified empirically rather than assumed.)
- **An immediate, friction-free retry path.** The customer should be able to come straight back into the same onboarding session and re-attempt Embedded Signup the moment they've deleted the stale entry, rather than restarting the whole flow — this is the one piece genuinely within your control, and it's where the "zero-friction onboarding" goal can still largely be honored even though the single click can't be eliminated.
- **An honest fallback for the case that can't be solved at all.** If the stale WABA sits under a business the customer does *not* personally administer (a forgotten former agency or BSP), no product design closes that gap — the approval authority belongs to a third party with no relationship to your app, and Meta's own documented fallback is a support ticket or developer-community thread, not a self-serve flow of any kind. The product should detect this distinction where possible (e.g., ask the customer directly, since there's no API signal for it) and set expectations accordingly rather than implying a fix is one click away when it structurally isn't.

## Conclusion

The most useful reframe from this research is that "can we automate this" was the wrong axis of investigation — the deletion operation that actually fixed your test case has never been exposed as an API call by Meta, for any partner, at any access tier, so there is no integration work that unlocks it. What is left to engineer is detection fidelity (knowing which of three distinct Meta-side operations a given rejection actually requires) and the quality of the hand-off (making the one unavoidable click feel like a guided, understood step rather than an unexplained ejection from your product). Treat the manual Business Suite deletion as a permanent fixture of onboarding for this failure class, not a stopgap, and design the surrounding UX — error-specific messaging, an immediate retry path, and honest signaling when the blocking business isn't the customer's own — as the actual deliverable.
