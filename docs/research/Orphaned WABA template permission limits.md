# Orphaned-owner WABAs hit an undocumented wall

No source anywhere — Meta's own documentation, its developer community forum, Stack Overflow, GitHub, or any BSP's support docs — contains the literal error string "(#100) Need permission on either WhatsApp Business Account or owner/shared business," and no source documents a causal link between an owning Business's Unverified status and a template stuck in PENDING past 24 hours. Both symptoms are, in the narrowest sense, undocumented. But a clear structural explanation exists for the first problem: Meta's own Embedded Signup and System User documentation draws a consistent, if scattered, line between actions a partner/Tech Provider can perform on a shared WABA (create templates, send messages, add numbers, assign users) and actions reserved to the client/owner business (delete the account, change settings, unshare it) — and template deletion falls naturally into the owner-reserved bucket, matching the create-works/delete-fails pattern exactly. For the second problem, no comparable mechanism was found: Meta's documented review SLA is a flat "up to 24 hours" with no verification carve-out, and the closest documented analog — a hard, immediate block on AUTHENTICATION-category templates for low-trust accounts — is a different failure mode (instant rejection, not multi-day limbo) that several developers report verification alone does not fix. No workaround short of the owning business acting was found for either problem; every documented remediation path for Meta's asset-permission model routes through an admin action on the owning side. The broader implication is the one worth acting on: this specific orphaned-owner scenario (Embedded Signup abandoned mid-flow, WABA partner-shared but never claimed by a real owner) appears to be essentially undocumented in public sources, which means the number recovered this way should be treated as running on a shrinking set of guarantees — safe for messaging and template creation today, but at risk the moment any destructive, settings-level, or scale-gated operation is attempted.

## The delete/edit failure fits a documented ownership boundary, even though the exact string doesn't

Meta never publishes the error text you're hitting, but it doesn't need to for the failure to make sense. The Embedded Signup "Manage Accounts" page is the clearest primary-source statement of the boundary: a partner can add phone numbers, create templates, send messages, assign users, and view metrics/payment info on a shared WABA, while the client/owner alone retains the ability to unshare the account, **delete it**, and **change settings** — and Meta states flatly that a partner "cannot disable what your clients can see or do" ([Manage Accounts](https://developers.secure.facebook.com/docs/whatsapp/embedded-signup/manage-accounts)). That line — create/send/add are partner-permitted, delete/unshare/settings are owner-reserved — maps directly onto your symptom: creating, listing, and sending all work under the System User token because they sit in the partner-permitted bucket, while deleting or editing an existing template sits in the same administrative bucket as "delete the account" or "change settings," which Meta's own docs say partners cannot touch regardless of what OAuth scopes or task grants they hold. This is corroborated independently by 360dialog's documentation of the inverse On-Behalf-Of model, where the client (there, playing the role your orphaned owner plays) cannot remove a phone number at all — only the party structurally positioned as "owner" can, and everyone else must escalate ([360dialog WABA Management](https://docs.360dialog.com/partner/waba-management)). The pattern is about which party is the asset *owner*, not a fixed read-versus-write rule, and it recurs: Meta's permissions documentation requires a partner's app to clear an **Advanced Access** App Review gate specifically to manage, via `whatsapp_business_management`, any WABA the partner's own business doesn't own, returning a generic error code 200 if that's missing ([WhatsApp Permissions](https://developers.facebook.com/documentation/business-messaging/whatsapp/permissions)) — a different code than the one you're seeing, but the same underlying architecture of "owning the asset is structurally distinct from being granted access to it." One alternative explanation is worth ruling out before concluding this is pure ownership-gating: Meta's own help documentation states that templates provisioned *by a Solution Partner* through Embedded Signup — i.e., partner-supplied default templates — "can't be deleted" at all, by anyone, through the normal delete flow, regardless of caller identity ([Delete message templates, via chatarchitect mirror](https://support.chatarchitect.com/books/meta-whatsapp-business-platform/page/delete-message-templates-for-your-whatsapp-business-account)). If the specific templates you're failing to delete originated that way, this template-provenance rule — not owner-vs-partner access — would be the actual cause, and is worth checking first since it has nothing to do with the orphaned-owner situation at all.

No source confirms exactly which named task governs delete specifically. Meta's "Manage System Users" documentation lists the granular tasks assignable on a shared WABA — `DEVELOP`, `MANAGE_TEMPLATES`, `MANAGE_PHONE`, `VIEW_COST`, `MANAGE_EXTENSIONS`, `VIEW_PHONE_ASSETS`, `MANAGE_PHONE_ASSETS`, `VIEW_TEMPLATES`, `VIEW_INSIGHTS`, `MANAGE_USERS`, `MANAGE_BILLING` — and names `MANAGE_TEMPLATES` as the template task, but never states whether that task covers delete as distinct from create/edit ([Manage System Users](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/manage-system-users/)). The same page notes that the broader admin-equivalent `MANAGE` task "will only work if you are given full access on the solution i.e. including MESSAGING" — implying a tier above the granular tasks exists, but framed around a `MESSAGING` grant, not around owner status specifically. Critically, granting *any* task — including re-sharing with broader `MANAGE` access — itself requires "the access token of a System User with admin permissions" on the owning side, meaning even the most generous documented workaround (asking for a wider task grant) still routes through an action only the owning business's admin can take. No source describes a lesser workaround, and no source confirms or denies that re-sharing with full `MANAGE` would even fix this specific error — it would be a reasonable thing to test, but it isn't a documented fix anywhere found.

## The PENDING stall has no documented tie to Unverified status — and is probably a different problem than you think

Meta's own template-review page is unambiguous and makes no exception for account trust: approval decisions "can take up to 24 hours," and appeals of rejected templates are decided within the same window, full stop — the only documented levers over outcome are content and formatting issues (brace/variable mismatches, policy violations, character limits, duplicate body+footer text) that cause **rejection**, not an extended pending state, and Business Verification is never mentioned as a review-speed factor anywhere on that page ([Template Review](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-review/)). Two independent BSPs corroborate the same window with the same absence of a verification caveat: 360dialog cites "up to 24 hours" and tells partners to simply contact Meta support if it runs long, while Telnyx documents a 24–48 hour norm (with authentication templates typically approved in minutes) and flags anything beyond 48 hours as warranting investigation ([360dialog](https://docs.360dialog.com/partner/messaging/template-messages/template-statuses); [Telnyx](https://support.telnyx.com/en/articles/13986489-whatsapp-troubleshooting-guide)). The only vendor source claiming verified businesses get faster or "immediate" approval is an unauthenticated guide whose claim could not be corroborated against any primary Meta page, and should be treated as folk wisdom, not fact.

What *is* documented is a different, easily-confused failure mode: a long-running Meta Developer Community thread, active across more than a year with many independent reporters, describes **AUTHENTICATION-category templates being hard-blocked** at the account level — an immediate "does not have permission to create message template" error, not a slow pending state — for accounts on the 250-message unverified tier with little traffic. Notably, one credible reply in that thread reports that business verification *alone did not unlock the category* in the cases he observed; he lists verification, adding a payment method, and building utility-message volume together as the cluster of signals that seemed to matter, with no confirmed fix from Meta staff anywhere in the thread ([Meta Developer Community](https://developers.facebook.com/community/threads/1372007877817645/)). This is instructive for your case precisely because it's a *different* symptom (instant block vs. multi-day limbo) that superficially looks related — if your stuck templates are AUTHENTICATION category, you may be looking at this known, documented, unresolved block rather than a true PENDING stall. If they're Marketing or Utility, the stronger analog is a separate Meta Developer Community thread, "My WhatsApp message template has been pending for 4 days," where multiple unrelated developers report multi-day stalls with **no discussion of business verification at all** — the only suggested remedy (from a fellow developer, not Meta) was trying creation via direct API instead of WhatsApp Manager, never confirmed to work ([Meta Developer Community](https://developers.secure.facebook.com/community/threads/921397146476266)). Separately, there is at least one documented case of Meta acknowledging a genuine platform-wide review backlog with no connection to any individual account's standing, during a June 2025 incident where Meta stated it was "working through the backlog of pending templates" platform-wide ([Bird status incident](https://status.bird.com/incidents/r4vshkk7637c)) — a reminder that a long pending window is sometimes just Meta's queue, not a signal about your account.

You've already ruled out the most common false lead here by re-fetching directly from the API rather than trusting a webhook: this instinct is backed by documentation. Telnyx's troubleshooting guide explicitly states "the template may already be approved or rejected on Meta's side while [the platform] still shows PENDING... Meta Business Manager is the authoritative source," confirming that `message_template_status_update` webhook delivery is a known, real point of desync, distinct from the underlying API state ([Telnyx](https://support.telnyx.com/en/articles/13986489-whatsapp-troubleshooting-guide)). No source anywhere suggests the reverse — that a direct `GET` itself can return a stale or cached status — so your fresh re-fetch confirming true PENDING should be trusted as accurate; this just isn't a sync-lag artifact. Put together, the honest conclusion is that **no documented mechanism connects your owning business's Unverified status to this specific stall**, and the "real fix" supported by actual sources is the unglamorous one every source converges on for genuinely stuck cases: escalate to Meta/BSP support with the WABA ID and template name, since no self-service lever beyond that exists in anything found.

## Ownership-gating is the rule for destructive/admin actions — but the roster of what's exposed is only partly documented

The create-succeeds/delete-fails pattern you're hitting on templates is very likely not templates-specific — it's the visible edge of a general rule that Meta documents piecemeal rather than as one canonical table. The clearest *confirmed* extension is phone number deletion: Meta's Embedded Signup error documentation states that once a WABA hits its number cap, removing a number is handled by "the business admin of the WhatsApp Business account," following the standard owner-side delete-number flow, with the only alternative being direct Meta support escalation to raise the cap ([Embedded Signup Errors](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/errors)). WABA-level settings changes are explicitly named alongside delete/unshare on the same "Manage Accounts" page as owner-reserved, so any setting adjustment (beyond the template/number/user actions partners are explicitly granted) should be expected to hit the same wall. Everything else is a genuine gap, not a confirmed-safe zone, and the distinctions matter:

| Operation | Documented ownership gate? | Evidence |
|---|---|---|
| Template create/list/send | No — partner-permitted | "Manage Accounts" page explicitly lists these as partner-OK ([source](https://developers.secure.facebook.com/docs/whatsapp/embedded-signup/manage-accounts)) |
| Template delete/edit | Yes, by inference from the owner-reserved bucket | Same page reserves delete/settings to owner; matches your observed symptom |
| Phone number deletion (at cap) | Yes, confirmed | Business-admin-only per Embedded Signup error docs |
| WABA settings changes | Yes, confirmed | Explicitly named owner-reserved on "Manage Accounts" page |
| Flows deletion | **Different model** — status-gated, not ownership-gated | A published Flow cannot be deleted by *anyone*, owner or partner, until deprecated first (error 139004); it's a publish-state rule, independent of caller identity ([Flow error codes](https://developers.facebook.com/docs/whatsapp/flows/reference/error-codes)) |
| WhatsApp Calling enablement | Undocumented in ownership terms | No primary Meta page found addressing this for the abandoned-owner case; third-party sources (unconfirmed against Meta) claim Business Verification is required for calling eligibility |
| Conversational automation (welcome message, ice breakers) | Undocumented, and possibly orthogonal | 360dialog describes these as configured per phone number via WhatsApp Manager/API with no verification gate mentioned; separately, Meta's own Cloud API docs reportedly flag welcome messages as "not functioning as intended" for unrelated reasons |
| Billing/payment setup | Undocumented in ownership terms | `MANAGE_BILLING` exists as a named partner task specifically "for sharing a Line of Credit," but no source states whether an unverified/abandoned owner blocks this |

The practical read: **Flows are the one area that likely behaves differently than you'd expect by analogy** — rather than needing the owner to act, a stuck Flow just needs to be deprecated (a documented, callable action) rather than deleted outright, regardless of who's calling. Calling, conversational automation, and billing are the real unknowns; nothing in primary Meta documentation states whether an unverified, abandoned owning business blocks any of these, so they should be treated as "likely to break the same way templates did" purely by architectural analogy, not as confirmed. Separately from ownership, Business Verification itself documents a second, independent ceiling that compounds with the ownership gap: unverified businesses face a 250-business-initiated-conversation-per-24-hours cap and a template-count ceiling (250 approved templates vs. 6,000 verified) regardless of who's calling the API, per multiple BSP docs cross-referenced against Twilio's documented error 63104 for exceeding unverified phone-number limits ([Twilio Error 63104](https://www.twilio.com/docs/api/errors/63104); [Tally Solutions](https://help.tallysolutions.com/verify-business-with-meta/)). In other words, even once the ownership-gated delete/edit problem is somehow resolved, the unverified-owner status separately caps scale — two independent ceilings stacking on the same WABA, not one.

## This exact scenario is close to undocumented — escalation, not a workaround, is the realistic path

A dedicated search for prior cases matching your exact setup — a partner-shared WABA whose owning Business was auto-generated by an interrupted Embedded Signup and never verified, never given a payment method, never claimed by anyone — turned up nothing on Meta's Developer Community, Stack Overflow, GitHub, or any BSP's support documentation. The closest analogs are structurally different: a "phantom/ghost partner" problem (stale partner access lingering after a BSP migration, resolved by revoking it from the Business Manager side) and the general abandoned-Business-Manager-access problem, where in at least one Meta Developer Community thread, a business whose sole admin's account was restricted and never appealed was told by Meta support directly that "there is no way that we as the owners of the business can claim ownership" ([Meta Developer Community](https://developers.secure.facebook.com/community/threads/430771443211813)). At least one similar dispute (unrelated to WhatsApp specifically) was reportedly resolved only through a court case, not any Meta self-service process ([Cape Times](https://iol.co.za/capetimes/news/2023-11-27-facebook-battle-settled-as-nuri-sushi-owner-gets-sole-rights/)) — an extreme outcome, but a signal that Meta's documented self-service tools assume an admin exists somewhere to act, and your scenario may fall outside that assumption entirely.

Meta does document a legitimate ownership-transfer mechanism between Business Portfolios — Settings > Requests > Received, admin-approved or auto-completed after 30 days if not actively rejected — but every documented instance of its use (a 2025 Meta-mandated migration from BSP-owned to business-direct ownership, described by LivePerson, Exotel, and Freshworks support docs) is initiated by the *current owning/provider side*, never by a Tech Provider pulling a WABA away from an abandoned owner ([LivePerson FAQ](https://community.liveperson.com/kb/articles/2202-whatsapp-business-account-waba-ownership-transition-faqs); [Exotel FAQ](https://docs.exotel.com/messaging-apis/whatsapp-business-account-ownership-transfer-commonly-asked-questions)). Since your owning Business has no admin who ever logged in or completed setup, there's plausibly no one positioned to even receive or approve a transfer request on the losing side — which means this self-service flow may simply not be usable here. No source confirms whether a Tech Provider with only partner-level access has standing to *initiate* a transfer away from an unresponsive owner at all.

## Conclusion

The honest state of the evidence is that you're operating in a corner of Meta's platform that its own documentation never anticipated: Embedded Signup's docs describe a clean two-party model (an engaged client business and a partner), and every permission rule, transfer mechanism, and error code found traces back to that assumption. Your WABA has no engaged party on the owner side at all, which is why both your symptoms resist a tidy citation — the architecture degrades to "owner-reserved action, no owner available to reserve it for" rather than failing in a way anyone has written up. The most consequential takeaway for planning ahead is the risk map in the operations table above: treat Flows deletion as the one documented exception (deprecate, don't expect an ownership block), treat phone-number deletion and any settings change as confirmed to require the same owner action your templates need, and treat calling, conversational automation, and billing as unknowns that should be tested cautiously — ideally in a low-stakes way — before being relied on for this number, since no primary source rules out them hitting the identical wall. Given that no workaround short of owner action was found for the confirmed cases, and no public precedent exists for claiming an abandoned Embedded Signup artifact business, the realistic path forward is a direct Meta Partner/Developer support escalation armed with the WABA ID, the System User token's task grants, and the exact error text — not further searching for a self-service fix that the evidence suggests doesn't exist.
