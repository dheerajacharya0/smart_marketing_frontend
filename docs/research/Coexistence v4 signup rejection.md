# A dropped flag broke coexistence detection

frontend-DA's Embedded Signup still rejects a real WhatsApp Business app number with Meta's generic "already registered… disconnect it" error because a commit on October 25, 2026 (`741c3f9`) deleted the `extras.featureType: "whatsapp_business_app_onboarding"` payload from `lib/facebook-sdk.ts`, acting on the belief that Embedded Signup v4 "drops the extras payload entirely" and auto-detects coexistence server-side from the phone number alone. Meta's own documentation says the opposite: as of November 2026, v4 "continues to be supported through the `featureType` parameter," and the no-flag, pure-phone-number auto-detection the commit assumed is a **v5** characteristic that is not yet live (Meta's roadmap places it in H1 2027) ([Embedded Signup Versions](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/versions/), [Embedded Signup v4](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/version-4)). With `extras: {}` sent on every launch, Meta never enables the coexistence branch of the signup flow, the number falls through to the ordinary new-number registration path, and that path correctly (and unsurprisingly) rejects a number still live on the WhatsApp Business app — producing exactly the generic rejection text captured on the test device, down to its "up to 3 minutes" wording, which Meta documents as belonging to the **standard** phone-setup error table, not the coexistence-specific one ([Embedded Signup Flow Errors](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/errors.md)). The fix is narrow and code-only: reinstate the `featureType`/`setup`/`sessionInfoVersion` extras in `lib/facebook-sdk.ts`'s `FB.login()` call. The Meta Business Manager / App Dashboard side — the `config_id`, webhook subscriptions, Tech Provider status — is very likely already fine and is not where this bug lives.

## The October 25 commit removed the one flag that turns coexistence on

`frontend-DA`'s coexistence support was added correctly on October 6, 2026 (`7f8d01f`): `launchEmbeddedSignup(mode)` sent `extras: { setup: {}, featureType: FEATURE_TYPE[mode], sessionInfoVersion: "3" }`, where `FEATURE_TYPE` mapped `"coexistence"` to the literal string `"whatsapp_business_app_onboarding"` and `"new"` to an empty string. This matches Meta's only documented mechanism for enabling coexistence, which the dedicated coexistence doc describes explicitly: "Add a `featureType` property set to `whatsapp_business_app_onboarding` to the `extras` object," alongside `sessionInfoVersion: "3"`, in order to replace the generic account-selection screen with a "connect your existing WhatsApp Business account" option ([Onboarding Business App Users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users)). On October 25, three weeks after Meta's v2/v3 retirement deadline, commit `741c3f9` ("fix(whatsapp): stop sending the v2/v3-only Embedded Signup extras payload") deleted that entire `extras` payload, replacing it with a hardcoded `extras: {}` and a comment asserting that "v4 drops the extras payload entirely — coexistence is now detected server-side from the phone number entered in Meta's popup, not a client-sent flag." The commit message cites Meta's own v4 migration blog post as justification, specifically that the v2 `coex` feature type was excluded from auto-upgrade and silently falls back to the standard flow after October 15, 2026 — a true and well-documented fact ([Embedded Signup v4 blog post](https://developers.facebook.com/blog/post/2026/05/14/embedded-signup-v4/)). But that fact only establishes that the **old literal string `coex`** stopped working; it does not establish that **the `featureType` mechanism itself** was removed in v4. The commit conflated "the v2 feature-type value `coex` is deprecated" with "the v4 extras object no longer takes a feature-type value at all," and emptied the payload rather than updating the string to the still-current v4/v5 name `whatsapp_business_app_onboarding`.

## Meta's docs place true auto-detection in the future, not in v4

The research is unambiguous that v4, as currently shipped (November 2026), still requires the explicit opt-in. Meta's Embedded Signup Versions page lists `featureType: whatsapp_business_app_onboarding` as a supported v4 extras value in the same breath as the v4 "products" selectable on a Login for Business configuration (Marketing Messages API for WhatsApp, Click to WhatsApp Ads, Conversions API for WhatsApp) — none of which is a coexistence product, confirming coexistence is controlled purely by the client-sent flag, not by anything chosen in the Meta App Dashboard configuration object itself ([Embedded Signup Versions](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/versions/)). The v4-public-preview page states plainly that coexistence is **off by default** and "to opt in, launch Embedded Signup with `featureType` set to `whatsapp_business_app_onboarding`," and that "without the opt-in, a Business-app number is not treated as eligible for coexistence" ([Embedded Signup v4 Public Preview](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/version-4-public-preview/)). The only place "auto-detect with no client flag" appears in any fetched source is the description of **v5**, where onboarding is reportedly on by default and the flag is repurposed to opt *out* — and v5 sits in Meta's own account-model-evolution roadmap as a Phase 2, H1 2027 change that is explicitly "not yet detailed or shipped" as of this research. The roadmap's own language — "new Embedded Signup settings will control whether and where a Messaging account is created (details to follow)" — is the single official signal of a coming configuration-level coexistence control, and it is unambiguously a future state, not the current one ([Account model evolution / onboarding](https://developers.facebook.com/documentation/business-messaging/whatsapp/account-model-evolution/onboarding/)). The commit's premise, in short, borrowed a real v5 behavior and misapplied it to v4 three weeks early.

## The rejected error text is itself evidence of the missing flag

Independent of the config-requirements research, the flow-mechanics research reached the same conclusion from a different angle: Meta documents **two non-overlapping error tables**. The generic "Phone setup errors" table contains the exact message captured on the test device — "This number is registered to an existing WhatsApp account. To use this number, disconnect it from the existing account… It may take up to 3 minutes for the number to become available" — and its documented cause is that the number is "already registered on Meta's platform, meaning WhatsApp, the WhatsApp Business App, or the WhatsApp Business API," with the fix stated as "deregister the number if you want to use it, or register a new number" ([Embedded Signup Flow Errors](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/errors.md)). The **coexistence-specific** error table on that same Meta page uses different codes and different wording entirely — for example error 3441049 tells the user to wait 15 minutes, not 3, and error 3441047 is specific to Marketing-Messages-Lite WABAs. Because the device hit the generic table's exact wording, the attempt was processed as an ordinary new-number registration, not as a coexistence attempt that Meta then correctly rejected. This also resolves an apparent tension in Meta's own marketing: "keep using the app" is a claim about the dedicated, opt-in coexistence flow specifically (QR-scan linking, no phone-registration call) — it was never a claim that any Business-app number can be typed into any Embedded Signup phone field without friction. The two flows are architecturally distinct screen sequences; a genuine coexistence attempt replaces the account-selection screen with a "connect your existing WhatsApp Business account" option and never shows the generic "Enter a new phone number" field the test apparently reached ([Onboarding Business App Users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users)).

## Why the app-side config is probably not the problem

Three other places were checked and none shows evidence of being the gate. First, Meta Business Manager (`business.facebook.com`) hosts no coexistence-specific toggle in any source fetched, official or third-party — the "Embedded Signup configuration" is entirely a Meta-for-Developers object (the Facebook Login for Business configuration whose ID is `NEXT_PUBLIC_FACEBOOK_ES_CONFIG_ID`), and that object's only v4-relevant setting is which "products" are attached to it, which governs the Cloud API/ads/marketing-API surface, not coexistence eligibility. Second, the four webhook field subscriptions Meta requires for coexistence (`account_update`, `history`, `smb_app_state_sync`, `smb_message_echoes`, configured under App Dashboard → WhatsApp → Configuration) are read only **after** a number has already been successfully onboarded into coexistence — they govern contact/history sync and the `is_on_biz_app`/`platform_type` post-onboarding status check, not whether the initial signup screen recognizes the number as eligible ([Onboarding Business App Users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users)). They should still be verified present in the App Dashboard before retesting — a missing subscription would cause a different failure (contacts/history never syncing after a successful connect) — but they cannot produce an upfront rejection. Third, the claimed requirement that the developer be a registered Tech Provider/Solution Partner to use `whatsapp_business_app_onboarding` at all appears only in Meta's own prose describing who the coexistence doc is written for, with no source confirming it as an enforced gate that silently fails closed with the generic error; this remains an open item worth a direct Meta support check if the extras fix alone doesn't resolve the device test, but it is a weaker candidate than the missing flag.

## Residual eligibility gates to check once the flag is restored

Restoring `featureType` should let the device reach the actual coexistence screens, but several documented and vendor-reported conditions can still produce friction and are worth ruling out on the specific test number and device before concluding the fix failed. The WhatsApp Business app on the test device should be at version 2.24.17 or higher — multiple independent vendors cite this minimum, though none is Meta's own documentation and no source confirms it still applies verbatim in November 2026 ([engagelab](https://engagelab.com/de_DE/docs/whatsapp/quick-access/whatsapp-business-app-coexistence); [Wati](https://www.wati.io/en/blog/use-whatsapp-business-app-and-api-together/)). The WABA involved must not be configured for Marketing Messages Lite, which is categorically incompatible with coexistence and throws a distinctly-coded error (3441047), not the generic one ([Wati troubleshooting guide](https://support.wati.io/en/articles/11875544-troubleshooting-whatsapp-coexistence-signup-process-common-issues-and-how-to-resolve-them)). If the test number has **any** prior WABA/API history — even with a defunct provider — vendors describe an undocumented cooldown before Meta treats it as eligible again, with wildly inconsistent reported windows (7 days per one Eazybe guide, 30–60 days per Wati, 1–2 months per Chakra HQ); none of these figures comes from Meta directly, so they should be treated as approximate, not authoritative ([Eazybe](https://help.eazybe.com/en/articles/12964023-signup-troubleshooting); [Wati](https://support.wati.io/en/articles/11875544-troubleshooting-whatsapp-coexistence-signup-process-common-issues-and-how-to-resolve-them); [Chakra HQ](https://chakrahq.com/article/issues-whatsapp-coexistence-onboarding-setup/amp/)). India-specific country blocking is the least likely remaining explanation — vendor changelogs date India's removal from Meta's coexistence-unsupported list to mid-2025, well over a year before this test, though no Meta primary source confirms the current (November 2026) country list directly ([Freshdesk/LevelUp Pipeline](https://leveluppipeline.freshdesk.com/support/solutions/articles/153000242458-whatsapp-coexistence-live-in-india)). Finally, it is worth noting that two Meta Developer Community threads describe this identical error persisting for developers who insist their number is legitimately coexistence-eligible, with zero Meta staff response and no confirmed resolution in either thread ([thread #1635723110883422](https://developers.facebook.com/community/threads/1635723110883422/); [thread #969139072763031](https://developers.facebook.com/community/threads/969139072763031/)) — so if the extras fix and the checks above don't resolve it, escalating to Meta support rather than continuing to debug client-side config is the documented community's only path forward, since at least one of those threads hit a true backend bug with no self-serve fix (a number stuck sharing a WABA with a defunct former coexistence partner, with no in-app disconnect option).

## Conclusion

The practical fix is a two-line revert in `lib/facebook-sdk.ts`: change `extras: {}` back to an object carrying `featureType: "whatsapp_business_app_onboarding"`, `setup: {}`, and `sessionInfoVersion: "3"` for any launch where the number might already be on the WhatsApp Business app, since the October 25 regression was based on a documentation misread rather than an actual v4 behavior change. Because `components/connect-whatsapp-button.tsx` no longer asks the user to pre-declare "new number" vs. "WhatsApp Business app number" upfront — it relies on the (currently false) premise that v4 decides this itself — the simplest correct restoration is to send `featureType: "whatsapp_business_app_onboarding"` unconditionally on every launch rather than reintroducing the old per-mode branch, since Meta's documented v4 architecture is phone-number-first regardless: the flag only enables the coexistence detection branch, and a genuinely fresh number should still register normally through the same opted-in flow. `PROJECT.md`'s existing description of the integration ("`sessionInfoVersion` 3") is already stale relative to the shipped code and should be updated alongside the fix. The broader lesson for this integration is that Meta's v2→v4 and v4→v5 migration windows carry genuinely different, easily-conflated rules — the deprecation of the v2 literal `coex` string was real, but it was evidence for renaming a value, not for deleting the mechanism, and the next migration (v5, H1 2027) is where the "no flag needed" behavior the October 25 commit assumed will actually arrive.
