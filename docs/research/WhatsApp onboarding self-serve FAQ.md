# Codes, not FAQs, fix WhatsApp onboarding

Converszio already captures the one signal that separates a self-serve fix from a support ticket — Meta's structured `error_code` and `session_id`, parsed in `lib/embedded-signup-session.ts` and surfaced through the `ERROR` `postMessage` listener in `lib/facebook-sdk.ts` — but today that signal is thrown away before it reaches the customer: `components/connect-whatsapp-button.tsx`'s `ErrorView` renders only Meta's raw `error_message` text, never the code. Research across roughly **45 distinct failure modes in ten categories** (Facebook-account gating, WABA/number conflicts, business verification, display-name rejection, OTP delivery, popup/browser failures, post-connect messaging limits, and Meta account-security checks) shows that the *majority* of these carry a stable numeric or enum code Converszio's frontend can already branch on, while a real minority — mobile popup/opener loss, iOS popup blockers, in-app browser webviews, ad-blocker interference — produce no error event at all and need to be routed around, not explained. No WhatsApp BSP examined (360dialog, Wati, Gupshup) renders these codes contextually in-product; all of them fall back to a static, stage-organized reference article with human support as the backstop ([360dialog](https://docs.360dialog.com/partner/support-and-updates/help-and-troubleshooting/reaching-out-to-support/reference/troubleshooting-embedded-signup-issues), [Wati](https://support.wati.io/en/articles/11462949-troubleshooting-embedded-signup-process-common-issues-and-how-to-resolve-them)). That gap is the opportunity: the right design is not a bigger FAQ page, but closing the loop Converszio has already half-built — a single maintainable error-code map driving the existing `ErrorView`/`StatusNote` components, a short proactive checklist for the undetectable failure classes, and a static reference page demoted to a secondary, linked-out role for the handful of cases that genuinely need more room than an inline message, matching both NN/g's heuristic that **the fix belongs in the error message itself** ([NN/g](https://www.nngroup.com/articles/error-message-guidelines/)) and Twilio's proven pattern of **one stable code, one canonical doc, a thin in-product pointer** ([Twilio error 63114](https://www.twilio.com/docs/api/errors/63114)).

## Ten categories, and most of them already have a key to look up

The catalog splits cleanly by onboarding stage, which matters because it is also how customers experience the flow: they don't know whether they are looking at a Facebook problem, a WhatsApp problem, or a Converszio problem, only that something stopped them. Before a WABA even exists, **Category A** covers Facebook-identity gates — a too-new personal account, a Business Manager that already owns the maximum number of businesses, a disabled payment method, a signed-in user who isn't an Admin on the Business Manager they picked. Most of this category is only string-matchable (no stable code), with three exceptions that are fully code-addressable: CAPTCHA challenges, duplicate system-user names, and oversized WABA names. **Category B** (WABA creation) and **Category C** (phone-number registration) duplicate a large body of numeric codes this project had already catalogued in its coexistence-eligibility research (the `3441xxx`/`2655xxx` range — number tied to the wrong business, number already registered elsewhere, WABA restricted, phone-number limit reached), all genuinely auto-detectable since they arrive as `error_code` on the `ERROR` event.

**Category D**, business verification, turns out not to be a hard gate at all: Embedded Signup completes and messaging starts immediately for an unverified business — verification only caps the messaging-limit tier at Meta's base **250 unique users per rolling 24 hours**, shared across the whole business portfolio, with **2,000 as the next tier** reachable via verification, partner-verification, or 2,000 organic deliveries in 30 days ([Meta messaging limits](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)). Because this is a queryable account state rather than a one-off error, it belongs on a dashboard surface, not in error-recovery copy. **Category E**, display-name rejection, is the cleanest auto-detect case in the whole catalog: Meta exposes a `name_status` field (`APPROVED`, `DECLINED`, `PENDING_REVIEW`, `EXPIRED`, `AVAILABLE_WITHOUT_REVIEW`, `NONE`) directly on the phone-number resource ([Meta: Manage Phone Numbers](https://developers.secure.facebook.com/docs/whatsapp/business-management-api/manage-phone-numbers)), with the underlying webhook delivering a structured rejection reason for a declined name rather than free text — and critically, a rejected or pending name **never blocks messaging**, so the UI tone for this one category should be calm, not alarming. **Category F** (OTP delivery failures) is thinly documented even by Meta's own standards — most of what's known is vendor-sourced from a single BSP — but the practical fixes (switch SMS↔voice, don't hammer resend, landlines need voice-only) are stable enough to state proactively regardless of whether a specific code fires. **Category H** corrects a widely-repeated but **stale** claim: as of Meta's own page, live since October 2025, a quality-rating drop **no longer downgrades a number's tier**, and the old "Flagged" status no longer exists — it only blocks *further* scaling up ([Meta messaging limits](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)). Nearly every vendor doc found still describes the pre-2025 rule; Converszio's own copy must not repeat it. **Category I** (2FA/device-security challenges) and the generic **Category J** rate-limit catch-alls round out the set — both fully code-addressable, both genuinely about Meta/Facebook account standing rather than anything WhatsApp-specific, which argues for UI copy that explicitly says so ("this is a Facebook security step, not a problem with your WhatsApp setup") so customers don't blame the wrong product.

## A third of the failures never produce an error at all

**Category G** is the one place where a bigger error-code map cannot help, because there is no error to map. Converszio's code already documents the most damaging case: some mobile browsers open Meta's popup in a way that loses the `window.opener` link back to the page, so neither `FB.login`'s callback nor the `postMessage` listener ever fires (`connect-whatsapp-button.tsx`, the `STUCK_AFTER_MS` comment block). Research surfaced three siblings with the identical signature — silent, no event, same fix. iOS Safari's default popup blocker suppresses the popup with zero user-visible error, a mechanism confirmed in an unrelated but directly analogous Pega support case. Opening the signup link from inside Instagram's, TikTok's, or Facebook's own in-app browser triggers Facebook Login's own embedded-webview detection, which refuses to complete login by policy rather than erroring cleanly. And privacy/ad-blocker extensions sometimes misclassify Facebook's login popup itself as a tracker and auto-close it. All four share the same two properties: Converszio's side genuinely cannot observe them, and the fix is behavioral ("open this in your regular browser," "allow pop-ups," "disable the extension for this site") rather than diagnostic. The product's existing mitigation — a 45-second stuck timer that offers the no-popup guided wizard as an escape hatch — is the right pattern for all four, not just the one it was built for; the gap is that the hint only appears *after* the user is already stuck, when it could be stated as a one-line caveat *before* the popup opens, for mobile users specifically.

## The capture plumbing already outruns the UI consuming it

This is the most actionable finding in the research, because it's not a hypothesis about what Converszio *should* build — it's a specific, already-wired path that stops one step short of the customer. `launchEmbeddedSignup()` in `lib/facebook-sdk.ts` parses every `ERROR` event into `{ code, message, sessionId, timestamp }` and immediately calls `reportError()` with the code and session id attached — exactly what Meta's own documentation says to capture "when contacting support." But inside the same function, that parsed error is used for exactly one other purpose: if a later `CANCEL` event arrives with no `error_id` of its own, the code backfills `cancelled.errorId` from it (`lastError?.code`). Walk up the call stack from there: `EmbeddedSignupCancelledError` carries `cancel.errorId`, but `connect-whatsapp-button.tsx`'s `catch` block only ever reads `err.cancel?.errorMessage` to populate the `error` view (`else if (err.cancel?.errorMessage) setView({ name: "error", mode: chosen, message: err.cancel.errorMessage })`), and `ErrorView` itself takes a single `message: string` prop with no code field at all. The richest signal in the whole pipeline — a stable code plus a session id, present on-screen before the customer even closes the popup — is computed, reported to Sentry, and then dropped on the floor before it reaches the one place a customer could act on it. Fixing this is a plumbing change, not a research question: thread `code`/`sessionId` through the `error` view state and into `ErrorView`'s props, same shape the Sentry breadcrumb already uses.

## One error map, two surfaces, a feedback loop that already exists

The UX research gives a clear, if indirect, answer on *how* to use that code once it's threaded through. No controlled study pits contextual guidance against a FAQ page head-to-head, but NN/g's long-standing heuristic is unambiguous that **the remedy belongs in the error message itself**, with a help-page link treated as a secondary escalation only "when an error needs more explanation" and an explicit warning not to over-rely on it ([NN/g](https://www.nngroup.com/articles/error-message-guidelines/)). Proximity reinforces this for a popup flow specifically: the error state *is* "next to the element that needs attention" by construction, so routing the customer away to search a help center breaks the one advantage this flow has. Every BSP surveyed does the opposite in practice — 360dialog explicitly disclaims the errors as Meta's, not its own, and points to Meta's reference page first ([360dialog](https://docs.360dialog.com/partner/support-and-updates/help-and-troubleshooting/reaching-out-to-support/reference/troubleshooting-embedded-signup-issues)); Wati organizes a genuinely well-structured article by onboarding stage (sections A–F) with Cause/Fix lines per entry, but nothing in its own documentation claims it is linked from a live in-product error state ([Wati](https://support.wati.io/en/articles/11462949-troubleshooting-embedded-signup-process-common-issues-and-how-to-resolve-them)); none of the three demonstrate a dynamic, code-driven contextual banner. That is table stakes nobody has actually built yet in this space — which makes it a differentiator, not a parity feature, for Converszio to ship.

The maintainable version of this, modeled directly on Twilio's error-code pattern, is a single lookup — a new `lib/embedded-signup-errors.ts`, keyed by Meta's numeric/enum codes where one exists, each entry carrying a category, plain-language cause, a customer-doable fix, a `metaOwned` flag (so the UI can say "this is a Facebook security step, not us"), and whether retrying is sensible — with an explicit fallback bucket for anything unmapped ("Meta hit a temporary snag — wait a few minutes and try again"), exactly the "one source of truth plus explicit fallback" structure a Firebase's `AuthErrorMap` and independent error-mapper write-ups converge on ([Firebase AuthErrorMap](https://firebase.google.com/docs/reference/js/auth.autherrormap)). `ErrorView` renders from that map via the existing `StatusNote` component rather than the raw string, which also fixes the stale-information risk Category H exposed: the copy lives in Converszio's own map, not in whatever text Meta happens to send that day. Three refinements follow from the research rather than from the map itself. First, Meta's own error reference is a cautionary tale for exactly this architecture — a meaningful share of its ~20 topical tables are keyed by literal message text with no code at all, which is why a fallback path is mandatory, not optional ([Meta: Embedded Signup Flow Errors](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/errors.md)). Second, the undetectable Category G failures need a *proactive* line, not a reactive one: a short, dismissible addition to the existing "What you'll need" box in `ChooseView` — already present in `connect-whatsapp-button.tsx` — can state the mobile/in-app-browser caveat before the popup opens, which the literature frames as the correct complement to reactive help rather than a replacement for it ([Velaris](https://www.velaris.io/articles/proactive-vs-reactive-onboarding)). Third, the genuinely queryable states — business-verification status, current messaging-limit tier, quality rating — don't belong in error handling at all; they belong as a persistent stat tile on the WhatsApp settings surface, refreshed from the Graph API, because the "error" a customer hits there (a silent send failure once they're Restricted) is really a known account state surfacing late. A static, stage-organized reference page still earns a place — but only as the secondary layer `StatusNote`'s `action` slot links out to for the handful of categories that need more room than one inline message (business verification mechanics, the full display-name appeal process), mirroring Wati's and Meta's own stage-organized structure rather than a flat, searchable FAQ that research found no BSP actually uses as a first line of defense.

The map's maintainability doesn't require new instrumentation to track what's missing: every `error_code` already flows into Sentry through `reportError()` in `lib/facebook-sdk.ts`, which means an unmapped code shows up there as an unhandled breadcrumb the moment a real customer hits it — that becomes the backlog for the next row added to the map, closing the loop with the observability seam that's already shipped rather than building a second one.

## Conclusion

The research converges on a counterintuitive point for a product this size: building a conventional FAQ page would mean *matching* an industry pattern that the BSPs themselves treat as a fallback, not a solution, while Converszio already has the one piece of plumbing — structured `error_code`/`session_id` capture — that none of the surveyed competitors demonstrably expose to their own UI at all. The gap between what's captured and what's shown is a few hours of threading a prop through three files, not a research gap; the harder, more durable work is the single error-code map and the discipline of treating business verification and messaging limits as dashboard state rather than error copy. Shipping that turns Converszio's onboarding error screen into the thing NN/g has been describing as best practice for over a decade and that no WhatsApp BSP in this research has actually built: the fix, not just the failure, shown exactly where the customer is stuck.
